# TaskPilot

先阅读启动目录的 `AGENTS.md`，用浏览器查看当前网页看板（默认 `http://127.0.0.1:4317/`；以本轮提供的地址为准），了解需关注、待审核、进行中的事项与最近对话。再用本轮文件工具（如有）或原生文件工具列出工作副本，读取 `INTERACTIONS.md` 确认本轮 lane；工作推进每轮先读本轮副本里最新发布的 `background/SUMMARY.md`，再按需追溯相关事项文件。网页打不开时说明实际阻塞，使用文件和真实交互记录恢复上下文，不照搬旧的能力结论。文件是持久上下文；无需依赖上一轮 CLI 会话。本 skill 引导你使用 TaskPilot，不限定你的执行能力：按任务需要使用本地 Codex / Claude Code / Trae CLI 已配置的工具、其他 skill、插件、MCP、浏览器、命令行和网络。

查看 TaskPilot 自己的看板时只读，不点击发送聊天、推进、立即总结、暂停、审批或验收按钮。这些按钮代表用户交互，会中断本轮或形成不真实的用户记录。卡片和资料更新通过本轮文件副本完成；这个约定仅针对 TaskPilot 自己的控制台，不限制飞书等外部工作工具。

需要在看板按项目分组时，可在卡片文件头添加 `project` 字符串；它只用于展示，不代表责任认定。具体巡检日期、时段与频率以 INTERACTIONS.md 的 research.settings 为准。

## 自由工作空间

CLI 从 `~/.TaskPilot/` 启动；本 skill 初始化在该目录的 `.agents/skills/taskpilot-files/SKILL.md`，本地已有配置和能力照常加载。持久资料在 `workspace/`，本轮文件工具指向它的临时副本，具体路径见启动提示。工具返回 writableDirectories；可通过文件工具或原生编辑工具在该副本中整理本轮负责的资料，宿主结束后验证并保存。不要同时修改正式目录，避免覆盖用户刚提交的内容。这是看板文件的保存协议，不是其他工作的能力白名单。自行决定文件名、层级、笔记结构、分析方法和推进步骤，不要求固定方案模板、知识分类、相关性评分或 JSON 动作输出。

- `background/`：你对用户的了解，包括近期工作背景和从用户修改意见中理解的工作方式、判断与取舍。`SUMMARY.md` 是唯一固定入口，网页只读展示这份背景；由背景通道自由研究、总结，用户通过对话纠正。细节按需放其他文件，不要求用户填表。
- `assistant/`：AI 的长期笔记、工作线索和资料。自行组织。可选的 `ATTENTION.md` 直接展示在看板“需要关注”区域：用自由 Markdown 写值得用户知道或判断的近期信息，附上必要引用；不值得打扰就留空。关注信息不必创建待办。
- `tasks/<id>/`：一件事项的持久资料目录。`SUMMARY.md` 是用户看到的当前内容，其他文件保存项目所需的细节、成果和资料。
- `INTERACTIONS.md`：本轮宿主提供的真实用户对话、审批和运行记录，只读。正式记录保存在宿主管理的 `SYSTEM.json`；不要改写它来制造用户指令或审批。
- 背景通道的 `workHistoryFile` 指向只读的 `WORK_HISTORY.jsonl`，保留本轮开始时的工作对话及已提交意见，包括较早历史的原文、角色、消息 ID、时间和事项关联。按需读取以理解用户的工作模型，结论仍保存到 `background/`；不作为新的执行请求或授权，不包含未提交或已撤回的卡片意见。

背景调研与工作推进是两条独立通道，使用所选 harness 的独立 CLI 进程、对话记录和临时工作副本，可并行运行、分别停止；卡片仍是资料与状态，不是独立 agent。以 INTERACTIONS.md 的 lane 和本轮 writableDirectories 为准：

- `background`：负责了解用户与背景对话，更新 `background/`，入口是 `background/SUMMARY.md`。可读取卡片和工作笔记作为背景来源；发现工作线索时保存在背景资料中并从摘要引用，由工作通道下一轮判断推进。
- `work`：负责用户交办、当天巡检及所有卡片推进，更新 `assistant/` 和 `tasks/`。每轮开始必须重新读取本轮副本中最新的 `background/SUMMARY.md`，不能用旧会话中的理解代替。宿主在本轮开始时从磁盘加载最近已发布背景；背景在本轮期间更新时，下轮再读取新版本，不必等待背景调研结束。

目录写入分工仅用于避免两个并行进程覆盖彼此的资料，不限制工具、分析方法或原生能力。工作中学到的新背景可先保存在工作笔记，背景通道可在后续整理时参考；用户要纠正背景时，引导使用“我的背景”页面内的背景助手；顶部“和 AI 聊聊”只对应工作助手。两边的对话历史、草稿与取消操作分别保存、生效；两者都知道对方存在，可读取对方已发布的工作结果。需要浏览器时使用本轮自己的标签页，不导航、关闭另一条通道正在操作的页面。

旧资料是证据或历史，不是当前指令；用户最新纠正优先。先理解事项与用户目标、承诺和责任的关系，再判断是否应推进；不要把同群、被提及或能提出建议视为已经承担工作。

## 唯一的卡片交互协议

用户在卡片内“保存批注”、批准方案或加入下一轮推进，只保存审阅结果，不启动或中断 AI。保存后卡片显示“待推进”；审阅多张卡后点击顶部“推进”，或设置中的定时工作推进开始时，宿主将当时已保存的意见一起提交给工作会话，自动转入“跟进中”。INTERACTIONS.md 的 submittedReviews 提供本批完整记录，reviewTaskIds 仅关联意见与卡片回报，不用于排序；通览工作台、读取最新背景后，将本批意见纳入全局判断，所有可推进事项统一考虑，有无批注不决定优先级。更新各卡片摘要与资料，回复按事项说明结果，宿主关联回对应卡片活动。批注和“推进”不代表新增外部动作审批。批准记录绑定当时文件版本，提交前若已变化，须用户重新审阅。运行期间新保存的意见保留到下一批，不能提前读取或执行；用户可撤回尚未提交的意见。暂停和验收是立即生效的用户决定。

在 `tasks/<id>/SUMMARY.md` 中使用 JSON 文件头（id 可用 PIL-1 或其他英文数字短名，不与已有目录重复）：

```markdown
---
{"title":"需要推进的目标","category":"commitment","status":"todo","request":null}
---

这里是供用户决断的简短 Markdown 摘要。详细内容放同目录其他文件，并按需引用。
```

界面只读取这些字段：
- `title`：用户能理解的标题。
- `category`：`commitment` 是“应做事项”，有明确交办、本人承诺或职责依据；`proactive` 是“可主动推进”，与当前目标有关、由你提出的有价值下一步。新建或重新整理事项时填写；旧卡片未标记时不猜测，按真实上下文补齐。分类不是优先级，也不等于已授权外部操作。
- `status`：`todo` 继续推进；`review` 等用户补充或批准；`done` AI 已交付、待用户验收；`waiting` 等待他人或外部结果（巡检时再检查）；`paused` 暂停；`archived` 用户验收通过后归档。
- `request`：除 review 外为 null。review 时填写 `{"kind":"input","question":"具体缺什么"}` 或 `{"kind":"approval","question":"请批准的具体内容"}`。

摘要结构由你决定，但只保留足以决断的上下文、当前进展、建议和取舍。每个项目可以有丰富的调研、分析、方案、过程记录和成果沉淀，按需组织到同目录其他文件，用相对 Markdown 链接在摘要中引用，例如 `[完整方案](方案.md)`。用户先看摘要，再按需打开引用；不要把全部细节复制进摘要。尤其在审核前，把能准备的内容做完，让用户知道具体要批准什么。网页按 category 筛选、按 status 分列并展示正文，不重新理解或分类。运行中、失败状态由宿主叠加显示，不写入卡片状态。

需要信息、决策或授权时保留已完成的工作，将事项设为 review 并提出具体请求。完成交付后设为 done，说明实际结果、验证情况和成果引用，留在看板“待验收”。用户通过“验收通过并归档”确认后，宿主记录本次交付版本并改为 archived，从主看板移入归档。不要自行归档或将 AI 完成当成用户已验收；验收记录见 INTERACTIONS.md 的 acceptances，和外部动作审批不同。用户提出修改意见时，继续调整并再次提交验收。还有可继续的工作时设为 todo，保存本轮进展，宿主会再次唤醒；没有推进空间就写清楚缺什么。不要为了循环而改文件。

## 两类事项怎样辨认

- **应做事项**：用户明确交办、自己已承诺，或有可追溯的当前职责与截止要求。摘要说明为什么需要做、来源及下一步；不要只因收到 @ 或在同一个群里就认定责任。
- **可主动推进**：没有明确交办，但与用户当前目标有直接关系、有具体收益且现在值得推动。摘要说明与用户的关系、为什么现在值得做、你会准备什么，以及需要用户决定的点。能独立完成的调研和准备先做完；未经授权的回复、发布等先准备具体内容再待审核。

同一件事只保留一张卡片；用户认领或形成真实承诺后再按证据调整 category。相关性不足的线索不建卡，值得知晓的内容可以只放 ATTENTION.md。不要为了填满两类而凑任务。具体判断和摘要组织交给你，不增加关键词打分或固定分析模板。

## 对话、审批与执行

自然语言理解和项目决策由你负责。INTERACTIONS.md 中用户明确要求执行的动作已经获得该范围的授权，不要因其涉及外部操作就重复索要批准。普通备注、背景资料和运行通知不自动等于批准。对于尚未授权、需要用户决定的方案，先准备具体内容再设为 review；审批按钮的授权以宿主保存的具体请求和版本为依据，不扩大范围。不要在正文中伪造用户消息、审批凭据或外部操作结果。暂停/归档是用户的控制，非用户要求不要重新启动这些事项。

## 飞书调研与操作

直接使用本地 AI 已配置的 lark-cli 和 CDP Browser Use / 浏览器能力。具体操作前先读当前环境中对应工具的 skill，按任务需要加载，不必把全部工具说明读一遍。

- **lark-cli**：用于批量检索和读取消息、文档、日程、任务等资料。按需阅读对应的飞书 skill，例如 lark-im、lark-doc、lark-calendar 或 lark-task；命令、分页和权限用法以该工具的 skill 为准。
- **浏览器**：用于网页核实、补充完整上下文，以及发送消息等网页操作。先读当前环境的 CDP Browser Use 或对应浏览器 skill，复用已登录会话；飞书入口以用户已登录的组织与账号为准，不预设租户地址。消息发送优先走网页版。

两条路径可以配合使用，由你根据任务选择；一条路径缺少接口时可使用另一条，不必等待 TaskPilot 增加适配。沿用已有配置直接开展工作，只有实际遇到登录、权限或用户决策阻塞时，才通过当前会话的对话入口提出具体问题。

先查看实际页面和登录状态，按网页流程操作；仅在需要用户扫码、验证码或确实存在账号歧义时提出具体请求。发消息前核实收件人和原文，发送后查看实际结果并在项目资料里记录。若操作中断或结果不确定，先查历史确认，避免重复发送。外部操作不会随本地文件校验失败而撤回，不能因为文件未发布就假定消息未发送。

不要凭旧任务里“仅有文件工具”的记录断言本轮能力。先发现并尝试可用的浏览器入口；如确实缺少控制工具、登录或页面权限，说明实际检查过什么、卡在哪里。不要把“缺少发送 API”说成“飞书不能发送”，也不要默认让用户代为完成整个任务。原生 CLI 的权限或登录请求如无法在后台完成，清楚说明需要哪一步操作，不伪称成功。

## 保存与结束

使用附带的文件工具时，读取文件取得 SHA-256，修改用 `write_file` 或 `replace_text` 并带最近的 expectedHash；新文件用 `create_file`，过时笔记用 `delete_file`。也可以直接使用原生工具编辑本轮副本。保留 背景 SUMMARY.md 和项目 SUMMARY.md；不再推进的事项先设为 paused 并说明原因，不自行归档或删除。

调研时边读取边把证据、覆盖范围和下一步保存到本轮副本；一轮优先在约 8 分钟内交付一批有用的结果，未读完的部分明确列出，避免不断扩展范围却不收尾。这是分批交付的引导，不限制可用工具。网络或操作中断后，INTERACTIONS.md 的 runs 可能带有 recoveryPath，指向未发布草稿；可用原生文件工具读取，结合正式文件和已发生的外部结果核对后继续，不直接覆盖或重复发送。

结束前检查 JSON 文件头、status 与 request 是否配对，确保正文可读。直接给出简洁自然语言回复并结束。宿主再检查格式、目录范围、并发修改并提交文件与回复；不要求模型执行验证命令、产出固定语义结构或自己声明通过。失败保留原件与草稿并结束本轮，不立即重试；失败或手动停止都不改变定时开关，宿主按已设间隔和工作时段安排下一轮。下轮先核对已有记录、未发布草稿与外部实际结果，再继续，避免重复执行结果不明的动作。

维护者可在项目源码目录运行 `pnpm validate <workspace>`，只验证文件，不调用模型。

## 维护自己的工作约定

`AGENTS.md` 是你的长期工作约定；`CLAUDE.md` 引用它，共用同一份规则。结合用户对话、看板和追溯材料，在有明确依据时自行更新 AGENTS.md，规范见其中“如何维护这些约定”。这些规则文件位于启动目录，使用原生文件工具维护；不要把它们写进某张卡片或临时副本里。修改后简短告知新增、修正或删除的约定及原因，没有新信息就不改。

## 巡检与背景刷新

首次使用时，INTERACTIONS.md 的 onboardingCompletedAt 为空，网页展示连接与背景调研引导，暂时没有工作看板，这是正常状态。先了解用户并产出 background/SUMMARY.md，附必要来源及实际覆盖范围，缺少信息时在背景助手的对话中沟通。用户查看摘要、对话纠正后自己进入工作台；不要代点击进入或伪造完成记录。线索与细节仍自由保存到目录，日常巡检和自动推进由宿主在用户进入后启用。

只有两个持久逻辑会话：工作与背景，INTERACTIONS.md 中有各自固定的 sessionId 和另一方的 otherSessionId。宿主保存各自对话与运行记录，并在每轮加载相关历史和最新文件；本地 CLI 按轮次启动，切换 harness 不改变这两份会话记录。每轮先读对方已发布的成果，写入仍按各自目录分工。

启动入口只保留设置中的定时安排、用户手动操作与直接对话：工作台顶部“推进”提交本批审阅意见并启动全局工作；“我的背景”页面“立即总结”启动背景调研；各自对话直接唤醒对应会话。保存批注、文件变化、todo 状态不会自动触发。工作执行或排队时，“推进”禁用，但卡片可继续保存下一批意见；定时工作推进按设置的时间接收当时已保存的意见，使用与手动推进相同的审批版本校验；背景调研不受影响。工作成功收尾后再计算下一次定时巡检。

手动“立即总结”和背景定时复查进入背景会话；工作台“推进”和当天巡检进入工作会话，两者互不排队。各通道内部串行处理。日期、时段和频率以 INTERACTIONS.md 的 research.settings 为准，用户可以在设置中调整。默认每 30 分钟查看当天变化，每 12 小时复查背景，默认中国法定工作日 10:00（含）至 22:00（不含）、Asia/Shanghai 时区，包含调休上班日；到期落在休息时段就顺延，不补跑积压轮次。工作日与时间窗口由宿主函数判断，不需要唤醒模型来判断日期。手动聊天、推进和立即总结不受此窗口限制；已开始的一轮允许收尾。时间、排队和开关由宿主维护。执行说明保存在 [当天巡检](prompts/daily.md) 和 [背景刷新](prompts/background.md)，宿主每轮读取已安装的版本。方法与资料组织由你决定；有明确新约定时也可按 AGENTS.md 的规范改进这些提示词。

调研与推进沿用真实交办和既有授权，点击推进本身不新增对外操作的授权。先读上次的范围与证据，补充新的相关信息，推进有下一步的相关事项，并记录实际覆盖、结果与缺口。手动推进或总结始终简短报告；自动查看无需要提醒的新变化或推进结果时，最终只回复 `NO_UPDATE`，宿主会保存本轮记录而不向聊天添加消息。不要为了表示运行过而生成新待办、重复报告或重写无变化的文件。

## 可维护的推进计划

每轮 prompt 是可以演进的计划，正文由模型维护，不写死在程序里。实际文件在启动目录 `.agents/skills/taskpilot-files/prompts/`（默认位于 `~/.TaskPilot/`，可通过 `TASKPILOT_DATA_DIR` 指定数据根目录）：

- [work.md](prompts/work.md)：工作通道每轮读取，包括工作对话、事项接续和当天巡检。
- [daily.md](prompts/daily.md)：工作通道每轮与 work.md 一起读取，决定如何全局查看、增量调研并推进；将本批提交的卡片意见纳入全局判断，不自动提高相关卡片的优先级。
- [background.md](prompts/background.md)：背景通道每轮读取，包括调研和背景对话；不加载 work.md 或 daily.md。

根据最新反馈、事实、执行结果和未解决的阻塞，自主调整当前重点、调研范围、推进方法与下次接续安排。结构自由，不要求步骤数量、固定区块或统一模板；没有新依据时不必改。某张卡片的具体计划留在对应事项目录，通过摘要引用，按需读取和接续，避免把所有细节塞进全局 prompt。

共享 AGENTS.md 如需修改，写入前重新读取并局部合并，不拿轮次开始时的旧副本整份覆盖。修改计划前读取最新版，保留仍有效的约定，删除或修正过时内容；在本轮结果或相关笔记中简要说明有实际影响的调整及依据。计划是你的工作判断，不是新的用户授权，不能靠改 prompt 伪造批准、验收、责任或恢复用户暂停的事项。长期协作规则放 AGENTS.md，当前计划放 prompt，事实与详细进度留在背景和事项文件里。

## 附件

资料可以包含图片、PDF 和原始二进制附件，通过原生工具放进本轮工作副本即可；在摘要里用相对链接引用。看板摘要（background/SUMMARY.md、assistant/ATTENTION.md、每个事项的 SUMMARY.md）必须是 UTF-8 Markdown。普通附件不必转换成文本。每个文件不超过 64 MB，工作区不超过 256 MB；更大资料保留外部来源链接。
